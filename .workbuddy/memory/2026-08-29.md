## 修复详情拉取重试叠加（承接 2026-08-28 的排查）

把上一轮定位的"62s 连接超时放大"问题实际修掉了。三处改动：

### 1. `fetcher.build_pixiv_session()` — 传输层不再重试连接错误

```python
retry = Retry(total=1, connect=0, backoff_factor=0.5,
              status_forcelist=[429, 500, 502, 503])
```

`connect=0` 精确覆盖"连接建立失败"（超时/拒绝/DNS/代理，含 `ProxyError`）。429/5xx 与读取错误仍走 `total=1` 重试一次。

### 2. `fetcher._get_illust_detail()` — 连接错误 fail fast

在通用 `except requests.RequestException` **之前**新增：

```python
except requests.ConnectionError as e:
    logger.warning(f'Detail API 连接失败 {pixiv_id}: {e}')
    return None
```

顺序关键：`ConnectTimeout` 是 `ConnectionError` 的子类，而 `HTTPError` 不是——所以 401 仍能被后面的通用分支捕获并转成 `PixivAuthError`，`raise_for_status()` 的语义没被破坏。

分类结果：连接错误 → 立即放弃；403/429 → 退避 3s/9s 重试；其他（5xx、读超时）→ 退避 1s 重试。

### 3. `tests/test_app.py::test_detail_page_reflects_favorite_membership` — 预置 `original_urls`

`/detail/<pid>` 在 `original_urls` 为空时惰性调 `_fetch_original_urls()`。补上 `original_urls_list` 后彻底离线。

### 4. `tests/test_fetcher.py` — 新增 `TestDetailRetryPolicy`（4 个用例）

锁住上述分类语义，防止以后把重试又叠回去：连接错误只调 1 次、429 重试 `DETAIL_MAX_RETRIES+1` 次且退避、401 抛 `PixivAuthError`、session 的 `max_retries.connect == 0`。

用 `monkeypatch.setattr(fetcher, '_total_limiter', _TokenBucket(6000))` 旁路全局令牌桶，避免受其他用例残留的 `_last` 影响而白白 sleep。

## 图库/灯箱加载慢 —— 定位并修复连接未复用

用户反馈"进入图库打开查看原图加载过慢，能不能加个中间层"。

### 调查结论

链路梳理（`/thumb/<b64>` 是已有的代理缓存层，不能简单说"加个缓存"）：

- 图库网格：`proxyThumb(r.thumb_url)` → `/thumb/<b64 of 250x250>`，`loading="lazy"`
- 灯箱打开：先用网格缩略图即时渲染 → `fetch('/api/detail/<pid>')` → 已下载取 `local_urls`（本地文件，快）；未下载取 `medium_urls`（`/thumb/<b64 of c/600x600/..._master1200.jpg>`）→ **缓存未命中时要回源 Pixiv**

**真正的瓶颈不是缺缓存，是连接没复用。** 两个热点路径都在循环里 `build_pixiv_session()`：

1. `routes_gallery.thumb_proxy` —— **每张图**新建 Session + `close()`
2. `fetcher._fetch_details_parallel._worker` —— **每个作品**新建 Session（搜索一次 24~60 个作品就是 24~60 次握手），且从不 close（连接泄漏到 GC）

`build_pixiv_session()` 每次 `HTTPAdapter()` → 新的 urllib3 `PoolManager`，`close()` 后池销毁，等于每次重做 TCP + TLS 握手。

**实测**（沙箱无外网，用本地 `http.server` 统计 TCP 连接数，无 TLS）：
30 次请求 → 每请求新建 Session = **30 条连接**；复用一个 Session = **1 条**。本地耗时 87.6ms → 27.3ms（无 TLS 就已 3.2 倍）。真实环境每条连接还要付 1~2 个 RTT 的 TLS 握手，图片越小占比越高。

### 修复

- `fetcher.py` 新增 `_thread_local` + `_cookie_file_stamp()` + `get_pooled_session()` + `reset_pooled_session()`。按线程缓存（不跨线程共享，因为 `requests.Session` 不保证线程安全）；Cookie 文件 mtime 变化时自动重建，保证设置页改 Cookie 立即生效。
- `_fetch_details_parallel._worker` 改用 `get_pooled_session()`。
- `thumb_proxy` 改用 `get_pooled_session()`，并加"快失败重试一次"`——`复用连接被对端单方面关闭时 `connect=0` 不会自动重试，重建池再试；`requests.Timeout` 不重试（那才耗时）。
- `config.py` 新增 `THUMB_CONCURRENCY = 12`（原硬编码 6），`runtime.py` 的 `_thumb_sem` 改用它。

### 关键认知：为什么用线程内缓存而不是全局共享

生产是 `gunicorn -w 1`（**sync worker，单线程串行处理请求**）——所以线程内缓存在生产环境等价于全局复用，一张页面的所有图片共用一条 keep-alive 连接。开发用 `flask run`（`threaded=True`，每请求一线程）则复用有限，属预期，不会比改前更差。
`pool_maxsize` 默认 10 无需调：sync worker 同一时刻只有一个请求在跑。

⚠ 顺带发现（未处理，需用户决策）：sync worker 意味着**图片是严格串行加载的**，这可能是比握手更大的因素。`gunicorn -w 1 --threads 8` 能在保持单进程内存状态（`-w 1` 语义）的前提下并发处理请求 —— 内存状态是进程级的，线程共享，理论上兼容。但需评估线程安全后再上。

### 结果

220 passed in 12.99s（原 216 用例；新增 `TestPooledSession` 4 个用例：同线程复用、跨线程隔离、Cookie 变更重建、reset 丢弃）。

## 用户拍板"按你的想法来" → 线程安全审计 + 开启 `--threads`

### 决策依据

`runtime.py` 的内存状态是**进程级**的，`-w` 必须为 1；但线程共享同一进程内存，所以 `--threads N` 在保持单进程语义的前提下提供并发。而 gunicorn 默认 sync worker **一次只处理一个请求** —— 一页 24 张图严格串行加载，这很可能比握手开销还大。

### 审计结果（4 处真问题，全部已修）

1. **限流器（最严重，安全控制）** —— "读窗口 → 判定 → 记录 → 清理"拆成无锁多步，并发请求各自读到未计入对方的 records，同时通过判定。已把整段移入 `_rate_limit_lock`，并抽成可测的 `_check_rate_limit(ip, max_attempts, window) -> bool`。
2. **`download_locks`** —— `finally` 里无条件 `pop`；任务 A 在 release 后、pop 前被抢占时，B 会拿到 A 那把已释放的锁开始下载，A 随后把它 pop 掉，C 再进来拿到全新锁 → 同一作品并发下载两次。已加 `_download_locks_guard`，并把收尾抽成 `_release_download_lock(pid, lock)`（只删自己那把）。
3. **`_thumb_failed`** —— 清理是 Python 层推导式，遍历中被改动会抛 `RuntimeError: dictionary changed size during iteration`。已加 `_thumb_failed_lock`。
4. **两个 TTL 缓存时间戳写反** —— 先写 `ts` 再写 `data`，留下"时间戳新鲜、数据陈旧"的窗口。`_db_pids_cache` 更糟：`ts` 的赋值在 `with get_session()` 里、在整条 SQL 查询**之前**，所以窗口横跨整条查询（不是微秒级），会让已下载作品被误判成孤儿 → 同一作品渲染两张卡片、total 翻倍。已改成先 data 后 ts，且都放在查询完成之后。

**判定为安全、未加锁**：`_SEARCH_CACHE`/`_USER_PROFILE_CACHE` 本就有锁；键集合固定只改值的 dict（`_auto_follow_state`/`_prefetch_state`）无 size change 风险；`list(set)` 是单个 C 调用、中途无字节码边界，不会被抢入（但 Python 层 `for x in s` 会）。

**已知可接受**：`_last_fetch_stats` 并发搜索互相覆盖（仅影响前端统计展示）；TTL 缓存并发重建会重复扫盘/查表（宁可重复也不要脏数据）。

### ⚠ 重要教训：并发测试必须验证"去掉修复就会红"

第一版测试走完整 HTTP 请求（12 线程 + Barrier）→ 拆掉锁依然全绿，**测试无效**。原因：每个线程要穿过路由/session 等大量代码，撞进临界区的时刻被自然错开。

第二版直接压测 `_check_rate_limit`，60 线程 + `sys.setswitchinterval(1e-6)` → 仍然全绿。原因：临界区只有几微秒，默认 5ms 切换间隔下线程来不及在窗口内被抢占。

第三版才成功：把 `_rate_limit_store[ip]` 预置成自定义 `list` 子类，重写 `__len__` 为**先读出长度、再 `time.sleep(0)` 让出 GIL**，把线程切换强制塞进"已读到旧长度、尚未 append"的那一瞬。

复现率实测（`_YieldList` + 每轮 Barrier）：
| 配置 | 复现率 |
|---|---|
| total=8, limit=1 | **27/40（67.5%）** ← 采用 |
| total=12, limit=5 | 20/40 |
| total=16, limit=2 | 4/40 |
| total=40 或 100 | 0/40 —— 线程越多，Barrier 放行本身把线程拉得越开，反而打不中 |

单轮不够稳 → 跑 40 轮取最大值。拆锁时 3/3 稳定变红（最多放行 3 个 vs 上限 1，绕过 3 倍），装回锁后 5/5 稳定全绿，耗时 0.46s。

### 结果

225 passed in 14.06s（新增 `TestRateLimitConcurrency` 3 个 + `TestDownloadLockRegistry` 3 个）。

**1. 灯箱对已下载作品直接发全尺寸原图 —— 这才是"查看原图慢"的主因**

## 用户拍板"先做第二项" → image_cache 容量淘汰

### 实现

- `config.py` 新增三个常量：`IMAGE_CACHE_MAX_BYTES = 1 GB`、
  `IMAGE_CACHE_TARGET_RATIO = 0.9`（淘汰后回落到 90%，避免每次只删一点点反复扫描）、
  `IMAGE_CACHE_CLEANUP_INTERVAL = 300s`（扫描节流）。
- `helpers.py` 新增 `enforce_image_cache_limit(cache_dir, force=False) -> int`（返回删除字节数）：
  - 用 `os.scandir` 遍历，按 mtime 升序淘汰；
  - **安全底线**：只认 32 位十六进制 md5 命名的文件（可带 `.meta` 后缀），其他一律不动；
  - 非阻塞抢锁（已有线程在扫就直接跳过）+ 时间间隔节流；
  - `force=True` 跳过节流，用于启动兜底。
- 触发时机：`thumb_proxy` 成功写入缓存后调用；`app.py` 启动时 `force=True` 跑一次。
- 顺手消除 `CACHE_DIR` 的重复定义（app.py 与 routes_gallery.py 各写一份、靠注释约定同步），
  改为 app.py 从 routes_gallery import。

### 关键设计取舍：为什么是"最旧写入优先"而不是真 LRU

真 LRU 要在命中时刷新 mtime，但 Flask `send_file` 的 ETag 由 (mtime, size) 生成 ——
mtime 一变 ETag 就变，浏览器那 7 天的本地缓存会整体失效。所以选择不刷新 mtime。
代价：长期被看的旧图偶尔会被淘汰一次，随后自动重新成为最新，会自我修正。

### 测试（新增 tests/test_helpers.py，10 个用例）

覆盖：未超限不删、超限淘汰最旧的、`.meta` 随图片一起删、节流生效、`force` 跳过节流、
目录不存在是 noop。**重点是 4 个参数化的"不误删外来文件"用例**（`notes.txt`、`abc.jpg`、
32 位非十六进制名、`{md5}.jpg.bak`）。

**已验证测试有效性**：临时把 `len(base) != 32` 改成 `and False`，`abc.jpg` 那条立刻变红
（`int('abc', 16)` 会把它当成合法十六进制数）—— 说明这个安全测试确实在起作用，不是摆设。

### 结果

235 passed in 14.39s。启动清理已确认未误删现有缓存（66 MB / 2002 文件，远低于 1 GB 上限，
文件数完全不变）。
