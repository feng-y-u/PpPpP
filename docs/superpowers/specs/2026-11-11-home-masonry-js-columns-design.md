# 首页瀑布流改为 JS 分列（去掉 CSS 多列重排）设计

- 日期：2026-11-11
- 状态：已实现（2026-11-11，见文末「验证结果」）
- 相关代码：`pixivviewer/templates/home.html`、`pixivviewer/static/page-home.js`、`tests/test_home.py`

## 背景与问题

用户反馈：首页往下滚动加载更多时，**后两列的卡片会"看着看着就刷新"**，已经看过的作品被搬到别的位置。

根因是首页瀑布流用的是 CSS 多列（`home.html` 的 `.masonry { column-count: 3 }`）：

1. 多列布局是**列优先**：先填满第 1 列，再第 2 列、第 3 列。
2. 高度不限时默认 `column-fill: balance`（平衡列高）。每追加一批卡片，总高度变化 → 平衡点重算 → 断列位置整体前移。
3. 卡片高度各异 + `break-inside: avoid`，断点只能整张卡跳，位移非常显眼。
4. 每批 12 张分帧插入，一次加载会重排两次；懒加载 `IntersectionObserver` 跟着卡片位置走，图片在新位置才触发加载 —— 视觉上就是"刷新"。

注意：数据不是"按列请求"的，而是一整批 append 进同一个容器；跳的是浏览器的列分配。其余页面（`/explore`、`/gallery`、`/cache`）用的是 flex 行排（固定宽度、行优先），没有这个现象。

## 目标

1. 首页瀑布流**追加新卡片时，已落位的卡片不再移动**。
2. 保持现有视觉：纯图卡片、3 列（窄屏 2 列）、18px 间距（≤640px 为 8px）、卡片浮现动画。
3. 分隔条（`feed-divider`）仍横跨整行，仍只在第一批随机推荐前出现一次。
4. 跨断点（3 列 ↔ 2 列）时整块重排，**复用已有 DOM 节点**，不重新下载图片。

## 关键决策

### 用独立列容器，不用 CSS 多列

`#homeGrid` 变成普通块容器，内部由脚本创建若干「列段」（`.masonry` > 若干 `.masonry-col`）。新卡片只 append 进某一列，容器高度按列独立增长，浏览器不需要重新平衡列高 —— 已落位的卡片一次定位后永不移动。

CSS `grid-template-rows: masonry` 是原生正解，但 Chrome 不支持（Firefox 也只在 flag 后），不可用。

### 落点 = 当前最矮的列（最短列优先）

- 不能按 `i % 列数` 轮询：卡片高度各不相同（懒加载后才是真实比例），轮询会让列高越拉越偏。
- 每插入一张前读一次 `offsetHeight` 选最矮列，同高取最左 —— 相同视口 + 相同数据可复现同一分布。
- 代价：插入会强制一次同步布局（每批 24 张），在当前规模可忽略；换来的是列高均匀。

### 列高不可用时退回按序号轮询（实现后补钉）

首版只用「最短列」判定，部署后手机实测：**首屏卡片全堆进第 1 列、右边整列空白**。

原因：卡片 `<img>` 起始是占位 SVG（`data:` URI），解码前没有内在尺寸，所有列的
`offsetHeight` 都是 0；`0 < 0` 恒为 false，比较永远选第 0 列。已落位的卡片又"永不移动"，
所以第一屏整体挤在一列，直到后续批次才开始分散。

修正：先判断「是否至少有一列高度 > 0」。可用就按最短列；全为 0 就按
`band.placed % 列数` 轮询兜底（列段记录已放置张数）。轮询只保证分散、不追求等高，
列高确定后立即回到最短列优先。Node 模拟验证：8 张全零高度 → `0,1,0,1,...`；真实高度 500/200 → 选 200 那列。

### 列数由 JS 判定，CSS 只留间距断点

`column-count` 由 `matchMedia('(max-width: 992px)')` 决定（3 列 / 2 列），与旧 CSS 断点一致。CSS 只剩 `≤640px` 的间距收缩。**列数不能只写 CSS**：DOM 里列容器的个数必须与布局一致，否则隐藏的列会吞掉卡片。

### 重排时复用节点引用

脚本按数据顺序保留 `hotNodes` / `moreNodes` 两个节点数组。resize 跨断点时清空容器、按当前列数重建列段，再把**同一批节点**重新落位：`<img>` 的 `src` 已落地，浏览器直接用缓存渲染，不会重新发请求。只比较列数是否变化，同断点内 resize 不动 DOM（flex 自适应）。

### 分隔条恢复成普通块

原实现靠 `column-span: all` 横跨三列；去掉多列后它只是 `#homeGrid` 里的普通块，天然整行。两段内容各用一个列段：上段（热门）→ 分隔条 → 下段（随机推荐）。

## 取舍

- 随机推荐段的新卡片会落到该段最矮的列，可能出现在视口上方一点点（不在页面最底部）—— 这是最短列优先的固有行为（Pinterest 同款），相比"整页重排"轻微得多。
- 跨断点重排后卡片顺序仍按数据顺序重新分配，但视觉上会整体重排一次（用户刚改变窗口大小，可接受）。
- 不做严格的"节点高度缓存"：懒加载后图片高度变化会让列高不再严格均匀，瀑布流本来就允许这种不齐。

## 验证计划

1. `home.html` 不再出现 `column-count` / `column-span`。
2. `page-home.js` 用 `placeIntoColumns()` 把卡片挂进列容器（`renderInChunks` 仍只负责分帧调用）。
3. 源码级回归：新用例钉住"不能用 CSS 多列"，并更新原"卡片要显式插入"的断言。
4. `scripts/run_tests.ps1 -q` 全绿（基线 460 passed → 461+）。

## 验证结果

- 2026-11-11：`home.html` 的 `.masonry` 改为 `display:flex` 列段 + `.masonry-col`，删除 `column-count` / `column-span`；`page-home.js` 改为最短列优先追加，新增 `rebuildBands()` 处理跨断点重排。
- 新增用例 `test_home_masonry_uses_js_columns_not_css_multicol`，更新 `test_home_page_card_wiring` 的插入断言（不变式不变：调用方负责插入）。
- 测试：`scripts/run_tests.ps1 -q` → **462 passed / 2 skipped / 0 failed**（基线 460 passed，新增 2 条用例：禁 CSS 多列、列高不可用轮询兜底）。
- 补钉（2026-11-11，部署后手机实测"全挤第一列"）：`placeIntoColumns` 增加「高度全为 0 → 按序号轮询」兜底；Node 模拟确认零高度列 `0,1,0,1…` 分散、真实高度仍选最矮列。

- 未做浏览器内手工目测（本地未启动服务）；滚动不位移的不变式由「最短列优先 + 节点只追加」的结构保证。
