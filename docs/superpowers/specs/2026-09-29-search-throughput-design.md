## 背景与问题

项目使用 Pixiv 非官方 Ajax API。详情请求由三级令牌桶限制：前台详情 45 次/分钟、后台补全 20 次/分钟、全局 60 次/分钟。详情限速是为降低 403/429 风险，不应通过抬高速率来获得表面提速。

目前搜索任务通过 `/search` 异步提交，但 `/api/search/status/<task_id>` 只在任务完成后才看到最终 `results`；前端每 2 秒轮询一次。按画师搜索先从 `profile/all` 获取作品 ID，再对未命中已有详情的作品逐件调用详情 API；每页最多 24 件，收藏数/R18 过滤必须拿详情标签，因此冷搜索会受详情限速支配。项目已有详情线程池、取消检查点、详情预算、游标、缓存和连接池复用，这些行为须保留。

标签搜索默认 `min_bookmarks=0` 时会延迟详情，优先使用列表响应中的摘要数据；不应为了统一流程而给这一路径增加详情请求。标签搜索结果缓存当前 30 秒，画师搜索结果缓存 600 秒且带屏蔽标签指纹，用户作品 ID 缓存 600 秒。屏蔽标签增删会调用 `clear_search_cache()`。详情 403/429 当前按 3/9 秒逐条退避，多个任务同时受限时会放大等待。

此外，工作区存在未提交的 Pixiv 客户端适配层改造（`pixiv_client.py`、`fetcher.py` 与相应规格/计划/测试）。本设计以适配层职责稳定后的接口为目标，不覆盖或重置这批既有工作。

## 目标

1. 搜索仍在进行时，尽早展示已经确认符合筛选条件的结果。
2. 缓存命中和已有作品详情复用减少重复 Pixiv 请求；评估能否用用户作品摘要接口减少画师搜索的逐件详情调用。
3. 发生全局性 403/429 时停止请求风暴，以部分结果和明确状态结束搜索，而不是把受限作品静默过滤后缓存成完整结果。
4. 保持搜索过滤、页大小、预算、游标、取消语义和现有令牌桶速率不变。

## 非目标

- 不提高 45/20/60 次每分钟的令牌桶上限，不用代理/IP、账号或 Cookie 轮换规避 Pixiv 限流。
- 不放宽收藏数、R18 或屏蔽标签过滤，不提前把尚未验证的作品标为匹配。
- 不改用浏览器自动化或迁移到 PixivPy/其他客户端。
- 不承诺在 Pixiv 仍要求逐条详情且缓存未命中的情况下，缩短冷画师搜索的完整完成时间；渐进展示可以先改善首结果延迟。
- 不更改预取刷新策略、下载并发或图片 CDN 缩略图并发。

## 设计

### 1. 搜索任务进度与渐进结果

`routes_search._submit_search_task` 创建的任务继续存放在 `runtime._search_tasks`，并维持单进程语义。任务增加单调递增的 `revision`、进度计数（已检查、已确认、详情失败）和可选限流原因；`results` 表示截至当前已确认的累计结果。

`fetcher` 搜索流水线接收可选进度回调。仅当作品已通过该路径要求的筛选后，才发布到任务结果：

- 标签/发现列表摘要足够时，可按现有延迟详情语义发布摘要结果。
- 画师搜索在取得详情并通过收藏数/R18/屏蔽标签筛选后才发布该作品。

回调在 `_search_tasks_lock` 内以不可变快照更新累计结果和 revision；`search_status` 在同一锁下复制任务快照后再 JSON 化，避免状态轮询与列表更新竞争。状态响应保留现有字段，并增加 `revision`、`progress`、`complete` 与 `warning`；运行中的响应带当前累计 `results`。结果上限仍由现有页大小/预算约束，避免无限增大的轮询载荷。

前端 `static/page-index.js` 在 `status == running` 时按 revision 消费新结果，按 `pixiv_id` 去重并逐步更新网格；加载态保持，完成前不推进分页游标、不保存为完整页状态。完成后继续执行现有分页/搜索状态保存流程。现有 `searchGeneration` 仍负责忽略被新搜索取代的旧任务。

### 2. 可选用户作品摘要接口（有证据才采用）

在适配层中验证 Pixiv 是否有用户作品分页接口，可直接返回页面展示与筛选需要的摘要字段。只有脱敏 fixture 和离线契约测试证明所需字段完整、结构稳定且不改变结果语义时，才将其接入画师搜索，减少每件作品的详情请求。`profile/all` 的 ID 接口继续用于 ID 集合/游标来源；摘要接口不得绕过既有详情预算。

若找不到字段足够的接口，明确停止该分支，不猜测端点、不构造半真摘要；渐进展示、缓存和限流恢复仍可独立交付。

### 3. 搜索缓存与详情复用

- 保持画师搜索 600 秒缓存、用户作品 ID 600 秒缓存和数据库详情复用语义不变。
- 将标签搜索的结果缓存从 30 秒适度增加到 120 秒，使用独立标签 TTL，避免同步改变发现页/关注页缓存。
- 屏蔽标签变更后必须立即失效相关结果缓存；可沿用 `clear_search_cache()` 全清机制，或在缓存键中纳入 `_blocked_fingerprint`。测试必须证明屏蔽标签更新不会被旧结果遮蔽。
- 未完整完成、触发限流、预算中途耗尽或上游返回空错误的搜索，不得作为完整成功结果写入搜索缓存。成功缓存仍包含当前搜索过滤参数。

### 4. 详情请求并发与全局冷却

令牌桶速率保持不变。详情 HTTP 请求另设跨前台搜索与后台补全共享的在途上限 2，作为本项目已有“并发 3 时实测触发 403”的保守初值，防止慢请求重叠形成过高并发；线程池和限速桶仍负责排队，不以增加线程数突破请求频率。此上限可能在响应延迟较高时降低 45 次/分钟令牌桶的利用率，因此验收必须记录实际成功详情吞吐和 403 率；不得未经实测就提高上限。

限流状态放在 Pixiv 适配层的共享调度器中：

- HTTP 429 立即打开全局详情熔断；若响应包含有效 `Retry-After`，按其等待，否则初始冷却 60 秒。
- 连续 3 个不同作品详情请求在 60 秒内返回 HTTP 403 时打开熔断，避免把单个作品的权限/资源问题误判为全局风控。
- 熔断打开时不再启动新的详情请求；已在途请求可结束，但不再启动逐条限流重试。搜索任务保留已确认结果并以 `partial` 终止，附上可重试提示；不把受限结果计为“不匹配”。
- 冷却期满仅允许一个半开探测请求。成功后恢复并清除连续失败计数；再次受限则冷却时间指数增加，封顶 15 分钟。
- 连接错误、401、404 继续遵守已有分类，不能触发限流熔断。认证错误仍作为认证错误返回。

`partial` 是终态；过期任务清理逻辑需覆盖它。部分结果可供当前页面查看，但不得推进游标为“完整页”，不得写完整结果缓存。用户可稍后重新搜索；不自动无限重试。

### 5. 并发状态与模块边界

- 进度快照及熔断器的读-判定-写全程加锁；网络 I/O 不持有任务字典锁。
- 进度回调取消时不得继续发布旧任务结果；已经完成且通过筛选的数据库写入仍遵守当前入库事务和取消语义。
- 请求限速/熔断留在 `pixiv_client.py`（适配层职责稳定后）；分页、筛选、缓存及任务进度留在 `fetcher.py`/`routes_search.py`/`runtime.py`；前端只消费状态快照，不重新实现服务端筛选。
- 不破坏 `app` 命名空间测试补丁契约及 `-w 1` 单进程语义。

## 错误处理与分页语义

- `done`：完整页，允许提交游标、has_more 和成功缓存。
- `partial`：已展示部分结果，但本页不完整；保留输入页的游标位置，不宣称筛选结束，不写完整缓存，并显示限流/可稍后重试说明。
- `cancelled`：新搜索接管时按现有语义静默丢弃旧任务进度。
- `error`：维持认证失效及其他致命错误的既有响应语义。
- 状态轮询短暂重复会由 revision 与作品 ID 去重；旧 revision 不得覆盖新结果。

## 验收与测试

离线默认测试，不访问真实 Pixiv、不读取真实 Cookie：

1. 对后台搜索任务注入可控进度回调，验证运行中状态响应能返回已确认结果，revision 单调递增，完成态结果与最终返回完全一致。

3. 验证 429/`Retry-After` 打开冷却、半开探测成功恢复；连续 403 触发冷却；单个 403、401、404 和连接错误不会错误打开熔断。
4. 用假时钟/假 Session 验证熔断期不会启动新详情请求；在途结果可安全收尾；部分任务终止后不写成功缓存。

## 实施边界与顺序

1. 等当前 Pixiv 客户端适配层改造完成/稳定后再实施，避免同时编辑同一请求层。
2. 先实现进度快照与前端渐进展示、部分页分页语义及回归测试。
3. 再实现 429/连续 403 全局冷却及并发上限测试。
4. 在屏蔽标签失效测试通过后延长标签缓存 TTL。
5. 单独验证用户作品摘要接口；字段和测试不达标则不接入。
6. 跑全量离线测试，并用 mock 基线对比；不以提高请求频率作为优化手段。
